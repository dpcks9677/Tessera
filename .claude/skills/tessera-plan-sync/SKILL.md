# 계획서 동기화

대상: `$ARGUMENTS` (비어 있으면 계획서 전체)

당신은 오케스트레이터입니다. **불일치를 찾는 판단은 당신이 하고**, 문서 수정은 `tessera-scribe` 에 위임합니다.

계획서는 다음 세션이 어디서 재개할지를 결정하는 유일한 근거입니다. 틀린 채로 두면 다음 작업이 잘못된 지점에서 시작합니다.

## 대상 문서

구조와 상태 규칙은 `docs/plan/process.md`에 있습니다. 상태는 ID마다 한 곳에만 적습니다.

- `docs/STATUS.md` — 진행 포인터. 상태의 원본이 아닙니다.
- `docs/plan/roadmap.md` — 마일스톤 상태의 원본.
- `docs/plan/mNN/README.md` — 태스크(`Mnn-Tnn`) 상태·수락 기준·완료 기록의 원본.
- `docs/plan/mNN/T*.md` — 태스크 문서. 하위 작업(`Mnn-Tnn-n`) 상태의 원본. 머리말에 상태 줄이 있으면 그 자체가 규칙 위반입니다.
- `docs/plan/tracks/solid/README.md`, `docs/plan/tracks/improvement/README.md` — 트랙 태스크 상태의 원본.
- `docs/decisions.md` — 결정(`D-nnn`)과 미결정(`Q-nnn`).
- 세션 로그 — `docs/plan/mNN/log.md`, `docs/plan/tracks/*/log.md`, `docs/plan/log.md`. 모두 역순.
- `docs/archive/milestones/` — 보관된 마일스톤. 고치지 않습니다.

## 1. 기준선 잡기

먼저 마지막으로 기록된 지점을 찾습니다.

- 각 `log.md`의 **최상단 항목 날짜**. 역순이므로 이게 마지막 기록입니다.
- `docs/STATUS.md`의 **마지막 갱신일**.

그다음 실제 진행을 봅니다.

```bash
git log --oneline -20
git status --short
```

세션 로그 최상단 날짜 이후의 커밋이 있으면 그게 미기록 작업입니다.

## 2. 불일치 유형

아래를 찾습니다. 각 유형은 확인 방법이 다릅니다.

### 상태가 실제보다 뒤처짐
작업표에 `TODO` 인데 코드가 이미 구현된 경우. 가장 흔하고 가장 위험합니다. 다음 세션이 이미 한 일을 다시 합니다.

확인 방법: `tessera-scout` 에 "이 태스크가 지정한 파일에 해당 구현이 존재하는가"를 물으십시오. 여러 태스크를 확인해야 하면 서로 다른 태스크를 맡겨 최대 3개 병렬로 돌립니다.

### 상태가 실제보다 앞섬
`DONE` 인데 코드에 흔적이 없는 경우. 되돌려진 작업이거나 잘못 기록된 것입니다. 함부로 `TODO` 로 내리지 말고 커밋 이력을 확인해 어느 쪽인지 판단하십시오.

### 진행 포인터가 낡음
`STATUS.md`의 "진행 중 태스크"가 이미 끝난 태스크를 가리키거나, 태스크 표의 `DOING` 목록과 다르거나, "다음 행동"이 실제 다음 순서와 다른 경우.

### 세션 로그 공백
커밋은 있는데 해당 `log.md`에 대응 항목이 없는 경우. 커밋 메시지에 작업 ID가 들어 있으니 그걸로 대조하십시오.

### 상태 중복 기재
태스크 문서 머리말이나 본문에 상태가 따로 적혀 있어 README 태스크 표와 어긋나는 경우. 어느 쪽이 맞는지 확인한 뒤 README 표를 고치고, 태스크 문서의 중복 상태 줄은 지웁니다.

### 결정과 코드의 불일치
`D-nnn` 결정이 실제 코드와 다른 경우. 이건 문서만 고칠 문제가 아닐 수 있으니 **고치지 말고 보고**하십시오.

## 3. 확인 없이 고치지 말 것

**추정으로 상태를 바꾸지 마십시오.** 커밋 메시지에 `M17-T18` 이 적혀 있다고 그 태스크가 완료된 것은 아닙니다. 부분 작업일 수 있습니다.

각 불일치마다 근거를 확보하십시오.
- 코드에 실제로 구현이 있는지 (`tessera-scout`)
- 완료 조건이 계획서에 적혀 있다면 그 조건이 충족됐는지
- 테스트가 필요한 태스크면 검증이 실제로 돌았다는 기록이 있는지

근거가 없으면 상태를 바꾸지 말고 **"확인 필요" 목록에 넣어 사용자에게 물으십시오.**

## 4. 사용자 확인

수정 목록을 만든 뒤, **실행 전에 사용자에게 보여주고 확인받으십시오.** 계획서는 프로젝트의 기억이고 잘못 고치면 방향을 잃습니다.

보여줄 것: 어느 문서 어느 항목을, 무엇에서 무엇으로, 어떤 근거로 바꾸는지.

바꿀 것이 한두 개면 그냥 진행해도 됩니다. 상태 여러 개를 옮기거나 세션 로그를 새로 쓰는 규모면 반드시 확인받으십시오.

## 5. 수정

`tessera-scribe` 에 확정된 목록을 넘깁니다. 프롬프트에 담을 것: 문서 경로, 항목 ID, 현재 값, 새 값, 오늘 날짜.

기록 에이전트는 `docs/` 밖을 수정하지 않고 기존 표 형식을 그대로 따릅니다. 문서 여러 개를 동시에 고쳐야 하면 파일이 겹치지 않을 때만 병렬로 돌리십시오.

**세션 로그 항목을 지어내지 마십시오.** 실제로 무슨 일이 있었는지 커밋에서 확인되는 것만 씁니다. 확인 안 되면 "커밋 `abc1234` 기준" 처럼 근거를 남기십시오.

## 6. 보고

한국어로 보고합니다.

- 기준선: 마지막 기록 날짜와 그 이후 커밋 수
- 고친 것: 문서별로 무엇을 무엇으로
- 확인 필요로 남긴 것: 근거가 부족해 손대지 않은 항목
- 문서가 아니라 코드 쪽 문제로 보이는 것

**커밋하지 않습니다.**
