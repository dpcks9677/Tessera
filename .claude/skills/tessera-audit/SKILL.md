# 감사 오케스트레이션

감사 대상: `$ARGUMENTS`

당신은 오케스트레이터입니다. 렌즈별로 `tessera-reviewer` 를 **병렬로** 띄우고, 돌아온 지적을 중복 제거·정렬해 보고합니다. **코드를 고치지 않습니다.**

일반적인 정확성·단순화 리뷰는 이 스킬이 아니라 기존 `/code-review` 가 담당합니다. 이 스킬은 **이 프로젝트 고유 규칙 위반**만 봅니다. 두 개는 겹치지 않으니, 사용자가 범용 리뷰를 원하면 `/code-review` 를 안내하십시오.

## 1. 대상 확정

인자가 비어 있으면 변경분(`git status --short` 과 `git diff --stat`)을 대상으로 삼고 그 사실을 알립니다.

인자 형태별 해석:
- 파일 경로 → 그 파일
- 디렉터리 → 그 하위 전체
- `diff` 또는 `변경분` → 미커밋 변경 + 현재 브랜치가 `main` 대비 추가한 커밋
- 모듈명(`Tessera.Dice` 등) → 해당 네임스페이스 소속 파일

대상이 넓으면 좁히라고 요구하지 말고, 렌즈별 프롬프트에서 각자 우선순위를 두게 하십시오.

## 2. 렌즈 선택

대상에 **해당하는 렌즈만** 고릅니다. 셰이더만 바뀐 변경에 테스트 공백 렌즈를 돌리는 것은 낭비입니다. 보통 2~4개가 적당하고, 5개를 다 돌리는 경우는 드뭅니다.

선택한 렌즈와 그 이유를 사용자에게 한 줄로 알린 뒤 실행하십시오.

## 3. 렌즈 카탈로그

아래 명세를 **그대로 복사해** 각 `tessera-reviewer` 프롬프트에 실으십시오. 서브에이전트는 대화 이력을 물려받지 않습니다.

### 렌즈 A — SOLID 준수

`docs/agent/solid_refactoring_work_plan.md` 가 목표 구조를 정의합니다. 증강 시스템은 `IAugmentHandler` 와 발동 시점 인터페이스(`IOnAugmentSelected`, `IOnTurnStarted`, `IAfterScoreCommit`, `IOnTurnEnded`, `IBeforeScorePreview`, `IDiceCountModifier`, `IDiceLayoutProvider`, `IScoringDiceFilter`, `IScoreEnhancementModifier`, `ITurnDurationModifier`, `IManualActionAugment`)로 확장하게 돼 있습니다.

찾을 것: 증강 ID를 하드코딩한 `if`/`switch` 사다리, 신규 증강 추가 시 핸들러 밖 파일까지 고쳐야 하는 구조, 핸들러가 아닌 곳에 흩어진 증강별 분기, 단일 클래스가 규칙·표현·상태를 함께 들고 있는 지점.

주의: `YachtAugmentRuntime` 의 `Modification` 카테고리 공통 처리(`ResetFilledTarget`)는 **의도된 설계**입니다. `ModificationAugment` 의 XML 주석이 근거입니다. 이걸 위반으로 보고하지 마십시오.

### 렌즈 B — 아트 규칙

`AGENTS.md` §2와 `docs/reference/art_style_guide.md` 가 기준입니다. 코드나 머티리얼에 박힌 색·강도 값이 아래를 벗어나는지 봅니다.

- 키 라이트: 벽난로 골든 앰버 `#ff9e3b`, 2800~3000K, 강도 1.4~1.6
- 림/필 라이트: 쿨 인디고 `#364b6e`, 강도 0.35~0.5
- 배경: 딥 챠콜 `#0f0c10`
- 테이블 목재: `#6e432a` ~ `#825033`
- 러너 패브릭: `#882d22`, 놋워크 트림 `#e5a93c`

찾을 것: 팔레트 밖 하드코딩 색상, 규정 범위를 벗어난 라이트 강도, 실사 노이즈·주름·노멀 왜곡을 지향하는 셰이더나 머티리얼 설정. 스타일라이즈드 핸드페인티드 방향에 어긋나는 것.

### 렌즈 C — 직렬화 안전성

**이 프로젝트에서 가장 비싼 실수는 씬·프리팹 데이터 유실입니다.**

찾을 것: `[SerializeField]` 필드의 이름이나 타입이 바뀐 흔적, 필드를 프로퍼티로 바꾼 곳, 직렬화 대상 클래스에서 `[Serializable]` 이 빠진 곳, 프리팹 인스턴스의 오버라이드를 무효화할 수 있는 변경. 씬 저장 시 null 머티리얼 오버라이드가 새는 경로(커밋 `8083b1b` 에서 실제로 발생한 문제).

`MonoBehaviour`/`ScriptableObject` 를 상속하지 않는 순수 로직 클래스는 이 렌즈의 대상이 아닙니다.

### 렌즈 D — 아키텍처 경계

`AGENTS.md` §1이 모듈을 정의합니다. 루트 네임스페이스는 `Tessera`, 공통 시스템은 `Tessera.Core` / `Tessera.Dice` / `Tessera.Tabletop` / `Tessera.Rendering`, 게임별 모듈은 `Tessera.Games.AugmentedYacht`, 네트워크는 `Tessera.Network` 입니다.

**이 프로젝트에는 `.asmdef` 가 하나도 없습니다.** 모든 런타임 코드가 `Assembly-CSharp` 로 들어가므로 컴파일러가 경계를 강제하지 못합니다. 역방향 의존이 있어도 빌드는 통과합니다. 그래서 이 렌즈는 사람이 봐야만 잡힙니다.

찾을 것: 공통 시스템이 게임별 모듈을 참조하는 역방향 의존, `Tessera.Core` 가 `Tessera.Rendering` 이나 Unity 표현 계층에 묶이는 지점, 게임 규칙 로직이 `Presentation` 아래에 들어간 곳. 상태 소유권은 `docs/reference/architecture_decisions.md` 의 ADR을 근거로 삼습니다.

### 렌즈 E — 테스트 공백

EditMode 테스트는 `Assets/Editor/` 에 있고 26개 클래스, `[Test]` 약 213개입니다. `.asmdef` 가 없어 어셈블리 단위 필터가 불가능하며, 전체 실행에는 `UnitySkills.Tests.Core` 패키지 자체 테스트가 섞여 상시 실패합니다.

찾을 것: 변경된 규칙·계산 로직에 대응하는 테스트가 없는 지점, 기존 테스트가 검증한다고 착각하기 쉬우나 실제로는 다른 것을 보는 경우, 경계 조건(0, 음수, 빈 배열, 최대 라운드)이 비어 있는 곳.

지적할 때는 "테스트를 추가하라"가 아니라 **어떤 시나리오가 현재 무방비인지**를 쓰십시오.

## 4. 병렬 실행

선택한 렌즈 수만큼 `tessera-reviewer` 를 **한 번에** 띄웁니다. 각 프롬프트에 담을 것: 렌즈 명세 전문, 감사 대상의 구체적 파일 목록이나 범위, 이 변경이 무엇을 하려는 것인지의 배경.

**Unity REST를 쓰는 에이전트는 함께 띄우지 않습니다.** 리뷰어는 Unity에 접근하지 않으므로 리뷰어끼리는 안전합니다.

## 5. 통합

- **중복 제거.** 여러 렌즈가 같은 줄을 지적하면 하나로 합치고, 어느 렌즈들이 걸었는지 함께 적습니다. 두 렌즈가 동시에 잡은 지점은 신뢰도가 높습니다.
- **근거 검증.** 근거나 시나리오가 부실한 지적은 버립니다. 통과시키지 마십시오. 리뷰어가 규칙을 오독한 경우가 있으니, 판단이 서지 않으면 해당 파일의 그 구간만 직접 읽어 확인하십시오.
- **의도된 설계 걸러내기.** 주석이나 ADR에 설계 의도가 명시된 지점을 위반으로 올리지 마십시오.
- **정렬.** 치명 → 높음 → 중간 → 낮음.
