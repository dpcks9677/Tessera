# 버그 기록

인자: `$ARGUMENTS`

이 스킬은 기록만 합니다. **코드를 고치지 않습니다.** 수정은 사용자가 태스크(`/tessera-task`)나 직접 요청으로 진행합니다.

## 원본

- 폴더·번호·상태·심각도·영역 규칙: `docs/qa/README.md`. 시작할 때 읽습니다.
- 판정 어휘: `.claude/gates/README.md`

## `new <설명>`

1. `docs/qa/bugs/` 에서 가장 큰 번호를 찾고 다음 번호를 씁니다. 폴더가 비었으면 `BUG-0001`.
2. 설명에서 재현 절차, 기대 동작, 실제 동작을 가려냅니다. 빠진 것이 있으면 `AskUserQuestion` 으로 한 번에 묻습니다. 끝내 모르는 칸은 `미확인` 으로 둡니다. 추측으로 채우지 않습니다.
3. 환경은 직접 수집합니다. 브랜치·커밋(`git rev-parse --abbrev-ref HEAD`, `git rev-parse --short HEAD`), 미커밋 변경 유무, Unity 버전(`ProjectSettings/ProjectVersion.txt` 의 `m_EditorVersion`). 씬은 사용자 설명에서 가져옵니다.
4. 관련 코드 위치가 필요하면 `tessera-scout` 에 증상과 추정 영역을 넘겨 후보 위치만 받습니다. 원인 단정은 쓰지 않고 「추정」으로 표시합니다. 설명만으로 영역이 분명하지 않으면 이 단계를 건너뜁니다.
5. 아래 양식으로 파일을 만들고, 번호·제목·심각도를 사용자에게 보고합니다. 심각도는 근거 한 줄과 함께 제안하고 사용자가 바꿀 수 있게 합니다.

```markdown
# BUG-nnnn <한 줄 제목>

| 항목 | 값 |
|---|---|
| 상태 | `OPEN` |
| 심각도 | `S1`~`S4` |
| 영역 | <docs/qa/README.md 영역 중 하나> |
| 기록일 | YYYY-MM-DD |
| 관련 태스크 | <`Mnn-Tnn` 또는 없음> |

## 요약
## 환경
- 브랜치·커밋: <branch> · `<short-hash>` (미커밋 변경 있음/없음)
- Unity: <버전>
- 씬: <씬 이름 또는 미확인>
## 재현 절차
1. ...
## 기대 동작
## 실제 동작
## 기술 맥락
<scout가 찾은 후보 위치 `파일:줄`, 「추정」 표시. 없으면 「조사 안 함」>
## 증거
<로그, 스크린샷 경로, 테스트 이름. 없으면 없음>
## 확인 기록
## 종료 기록
```

## `verify BUG-nnnn`

1. 기록을 읽습니다. 이미 `CLOSED` 면 중단하고 알립니다. 수정이 어느 커밋이나 미커밋 변경에 들어 있는지 사용자에게 확인합니다.
2. 확인 수단을 고릅니다.
   - EditMode 테스트로 재현이 표현돼 있으면 `tessera-verifier` 를 **단독**으로 띄워 해당 테스트를 돌립니다.
   - 플레이 모드에서만 보이는 증상이면 재현 절차를 사용자에게 보이고 결과를 묻습니다.
3. 판정을 냅니다. `PASS`(증상 사라짐), `FAIL`(증상 남음), `NOT ASSESSED`(확인 수단 없음, Unity 미실행 등).
4. 「확인 기록」에 `YYYY-MM-DD <판정> — <수단과 근거>` 를 한 줄 추가합니다. `PASS` 면 상태를 `CLOSED` 로 바꾸고 「종료 기록」에 `YYYY-MM-DD 수정 확인` 을 적습니다. 그 밖의 판정은 `OPEN` 을 유지합니다.

## `close BUG-nnnn <사유>`

사유는 `재현 불가`, `의도된 동작`, `중복 BUG-nnnn`, `수정 확인` 중 하나입니다. 상태를 `CLOSED` 로 바꾸고 「종료 기록」에 날짜와 사유를 적습니다. `수정 확인` 은 `verify` 의 `PASS` 기록이 있을 때만 받습니다.

## 하지 않는 것

- 버그를 계획서 태스크로 자동 등록하지 않습니다. 필요하면 보고 끝에 태스크 후보로 제안만 합니다.

**커밋하지 않습니다.**
