# 태스크 실행 오케스트레이션

대상 태스크: `$ARGUMENTS`

당신은 오케스트레이터입니다. **설계 판단은 당신이 직접 합니다.** 조사·구현·검증·기록은 서브에이전트에 위임하고, 당신의 컨텍스트에는 그들의 요약만 들어오게 합니다.

빌드 로그 원문, 테스트 출력 전체, 파일 덤프를 당신의 컨텍스트로 끌어오지 마십시오. 그게 이 구조의 존재 이유입니다.

## 병렬 정책

- 파일 작업(조사·구현·문서)은 서로 겹치지 않으면 병렬로 최대 3개.
- **Unity 접근은 항상 단독.** `tessera-verifier` 가 도는 동안 다른 에이전트를 띄우지 않습니다. Unity Editor는 단일 인스턴스라 동시 접근 시 충돌합니다.

## 절차

### 1. 태스크 판독

ID 접두사로 계획서를 고릅니다.

- `SOLID-Tnn` → `docs/agent/solid_refactoring_work_plan.md`
- `Mnn-Tnn` → `docs/agent/work_plan.md` §7 (완료 마일스톤은 `docs/agent/milestones/completed.md`)

`Grep` 으로 ID를 찾아 해당 행과 상세 섹션만 읽습니다. 계획서 전체를 읽지 마십시오. 하위 계획서(예: `quill_hover_writing_animation_plan.md`)가 걸려 있으면 그것도 확인합니다.

상태가 이미 `DONE` 이면 중단하고 사용자에게 알립니다. `DEFERRED` 면 왜 미뤄졌는지 확인하고 진행 여부를 묻습니다.

인자가 비어 있으면 §2 현재 진행 포인터의 "현재 작업"을 대상으로 삼고, 그 사실을 사용자에게 알린 뒤 진행합니다.

### 2. 조사

`tessera-scout` 를 실행합니다. 프롬프트에 담을 것: 태스크 ID, 계획서에 적힌 목표와 대상 파일, 알아내야 할 구체적 질문.

서브에이전트는 대화 이력을 물려받지 않습니다. 필요한 맥락을 프롬프트에 전부 실으십시오.

범위가 넓으면 서로 다른 질문으로 최대 3개를 병렬 실행합니다. 같은 영역을 중복 조사시키지 마십시오.

### 3. 설계

**여기서 위임하지 않습니다.** 당신이 판단합니다.

- 변경할 파일과 각 파일에서 할 일을 항목으로 확정합니다.
- 기존 재사용 가능한 코드가 있으면 새로 짜지 않고 그걸 씁니다.
- 더 단순한 접근이 있으면 그쪽을 택하고, 계획서와 다르면 그 사실을 사용자에게 말합니다.

다음 경우 **멈추고 사용자에게 묻습니다.**

- 계획서의 지시와 실제 코드가 어긋난다
- 해석이 둘 이상 가능하고 결과물이 크게 달라진다
- `[SerializeField]` 필드 이름·타입 변경이 필요해 보인다 (데이터 유실 위험)
- 계획서에 없는 파일까지 손대야 한다

### 4. 구현

`tessera-implementer` 에 확정된 지시서를 넘깁니다. "잘 해봐"가 아니라 파일별 항목 리스트를 줍니다.

**파일 집합이 겹치지 않을 때만 병렬**로 최대 3개. 하나라도 겹치면 직렬로 돌립니다.

구현 에이전트가 "미해결 지점"을 돌려주면 임의로 무시하지 말고 설계를 다시 봅니다.

### 5. 검증

`tessera-verifier` 를 **단독** 실행합니다.

실패하면 원인을 판정합니다.

- 구현 실수 → 수정 지시서를 만들어 4번으로 되돌립니다.
- 설계 결함 → 3번으로 되돌립니다.
- 환경 문제(Unity 미실행, `currentMode` 가 bypass 아님) → 사용자에게 보고하고 조치를 요청합니다.

**같은 실패로 2회 되돌린 뒤에도 실패하면 중단합니다.** 무한 루프를 돌지 말고 사용자에게 상황을 보고하십시오.

### 6. 갱신

검증 통과 후:

1. `graphify update .` 를 실행해 지식 그래프를 최신화합니다. AST 전용이라 API 비용이 없습니다.
2. `tessera-scribe` 로 계획서를 갱신합니다. 프롬프트에 담을 것: 태스크 ID, 새 상태(`DONE`), 실제 변경 내용, 검증 결과, 오늘 날짜, 다음 작업.

### 7. 보고

한국어로 보고합니다.

- 무엇을 바꿨는지 (파일 나열이 아니라 "무엇을 왜")
- 검증 결과
- 남은 문제나 후속 작업
- 커밋 제안

**커밋하지 않습니다.** 프로젝트 규칙상 커밋 단위는 마일스톤이고, 매번 사용자 허가가 필요합니다. 태스크 하나가 끝났다고 커밋하지 마십시오. 마일스톤 전체가 끝났다면 변경 파일 목록과 커밋 메시지 초안을 제시하고 허가를 요청합니다.
