# 1·2단계 — 조사와 설계

## 1. 조사

`tessera-scout` 를 실행합니다. 프롬프트에 담을 것: 태스크 ID, 계획서에 적힌 목표와 대상 파일, 알아내야 할 구체적 질문.

서브에이전트는 대화 이력을 물려받지 않습니다. 필요한 맥락을 프롬프트에 전부 실으십시오.

범위가 넓으면 서로 다른 질문으로 최대 3개를 병렬 실행합니다. 같은 영역을 중복 조사시키지 마십시오.

## 1.5. 심문 (조건부)

조사가 끝난 뒤 설계에 들어가기 전에, 사용자에게 가정 없이 물어야 하는 태스크에서만 합니다. 다음 중 하나라도 해당하면 합니다.

- 수락 기준이 모호하거나 해석이 둘 이상이다 (`READY` 가 `CONCERNS`). 0단계에서 이미 사용자에게 물은 내용은 다시 묻지 않고 남은 모호함만 묻습니다
- 태스크 문서나 결정 기록에 열린 질문이 있다
- 새 기능이나 새 규칙을 만드는데 계획서가 동작을 한 줄로만 적었다
- 아래 2단계의 멈춤 조건에 걸린다

해당이 없으면 건너뛰고 바로 설계합니다. 대상·동작·검증이 계획서에 다 적힌 태스크에서 형식적으로 묻지 않습니다.

`grilling` 스킬(`mattpocock-skills`)의 설계 트리·라운드 방식을 따르되 아래 4가지를 덮어씁니다. 스킬을 호출하든 이 규칙만으로 진행하든, 충돌하면 이 규칙이 우선합니다. `grill-me`·`grill-with-docs` 처럼 추천 답을 요구하는 다른 심문 스킬도 같습니다.

1. **추천 답을 붙이지 않습니다.** `➡️` 줄과 「yes 로 수락」 어법을 쓰지 않습니다. 선택지는 나열하되 어느 쪽도 기본값으로 두지 않습니다. 사용자가 추천을 요구하면 그때 줍니다.
2. **모호한 답은 되묻습니다.** 「적당히」「보기 좋게」「빠르게」처럼 관찰하거나 잴 수 없는 답은 받아들이지 않고, 무엇을 보면 충족인지 묻습니다. 「합리적 기본값」으로 빈칸을 채우지 않습니다.
3. **심문 중에는 질문만 합니다.** 계획서·코드·결정 기록을 고치지 않습니다. 환경에서 알아낼 수 있는 사실은 `tessera-scout`·`tessera-reader` 로 찾고 사용자에게 묻지 않습니다.
4. **끝낼 때 요약합니다.** 확정된 결정, 근거 없이 둔 가정, 범위 밖으로 둔 것을 나눠 적고 「빠진 것이 있습니까」를 묻습니다. 사용자가 확인하기 전에는 설계로 넘어가지 않습니다.

심문이 끝나고 사용자가 요약을 확인한 뒤에, 결과를 설계 요약에 넣어 5단계 「설계와의 차이」 대조에 씁니다. 태스크 문서가 있으면 그때 「미결 질문」을 갱신합니다. 프로젝트 전반에 영향을 주는 결정이면 `decisions.md` 의 `D-nnn` 등록을 사용자에게 제안합니다.

## 2. 설계

**여기서 위임하지 않습니다.** 당신이 판단합니다.

- 변경할 파일과 각 파일에서 할 일을 항목으로 확정합니다.
- 기존 재사용 가능한 코드가 있으면 새로 짜지 않고 그걸 씁니다.
- 더 단순한 접근이 있으면 그쪽을 택하고, 계획서와 다르면 그 사실을 사용자에게 말합니다.
- 대상 파일에 해당하는 `.claude/rules/` 규칙과 어긋나지 않는지 봅니다.

다음 경우 **멈추고 사용자에게 묻습니다.** (1.5 의 방식으로 묻습니다.)

- 계획서의 지시와 실제 코드가 어긋난다
- 해석이 둘 이상 가능하고 결과물이 크게 달라진다
- `[SerializeField]` 필드 이름·타입 변경이 필요해 보인다 (`.claude/rules/serialization.md`)
- 계획서에 없는 파일까지 손대야 한다

확정한 설계 요약은 5단계 "설계와의 차이" 대조에 씁니다.
