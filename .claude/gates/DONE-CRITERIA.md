# DONE-CRITERIA — 태스크 종료 기준 대조

> 실행 주체: 주 세션 | 모델 티어: opus

**트리거**: 태스크를 `DONE` 으로 바꾸기 전. 모든 `review_mode` 에서 실행합니다.

**넘길 맥락**: 태스크 행의 수락 기준, 변경 파일 목록, `tessera-verifier` 의 컴파일·테스트 판정, 플레이 모드 확인 결과(있으면), `full` 이면 `CODE-REVIEW`·`TEST-COVERAGE` 판정.

## 점검 항목

1. **수락 기준** — 태스크 행의 수락 기준을 문장 단위로 하나씩 대조하고, 항목마다 증거(테스트 이름, 되읽은 값, 사용자 확인)를 붙입니다.
2. **공통 완료 기준** — `docs/plan/process.md` §6의 각 항목을 대조합니다. 증거 출처는 다음과 같습니다.
   - 테스트·콘솔 항목: `tessera-verifier` 판정
   - 플레이 모드 항목: 사용자 확인 또는 `tessera-unity-operator` 확인
   - 범위·매니페스트 항목: 변경 파일 목록과 `docs/reference/control_manifest.md` 의 해당 레이어 절
   - 기록 항목: 세션 로그와 `STATUS.md`

   태스크 성격상 적용되지 않는 항목(테스트만 추가한 태스크의 플레이 모드 확인, 새 규칙이 없는 태스크의 정상·경계·거부 사례 등)은 `해당 없음 — <사유>` 로 적고 판정에서 뺍니다. 사유를 댈 수 없으면 `해당 없음` 이 아니라 `NOT ASSESSED` 입니다.
3. **설계와의 차이** — 확정한 설계와 실제 구현이 달라진 점을 적습니다. 차이가 있으면 결정 기록이 필요한지 판단합니다.
4. **회귀** — 증강 변경이면 일반 요트 테스트도 통과했습니다(`process.md` §7.4).
5. **하위 게이트** — `full` 이면 `CODE-REVIEW`·`TEST-COVERAGE` 판정을 합칩니다.

## 판정

- `FAIL`: 수락 기준 미충족, 테스트 실패, 새 컴파일 오류·예외, 하위 게이트 `FAIL`.
- `CONCERNS`: 설계와의 차이가 기록되지 않음, 하위 게이트 `CONCERNS`.
- `NOT ASSESSED`: 테스트를 실행하지 못함(`MODE_FORBIDDEN` 등), 플레이 모드 확인이 남음. `process.md` §6에 따라 이 상태로는 `DONE` 으로 표시하지 않고, 이유와 필요한 검증을 로그에 남긴 뒤 사용자에게 묻습니다.
- `PASS`: 위 항목을 모두 충족.
