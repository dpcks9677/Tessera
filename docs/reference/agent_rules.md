# 에이전트 공통 작업 규칙

> **문서 종류**: 작업 규칙 (AI 대상)
> **코드 대조 기준**: 2026-10-24 · 커밋 `d7d59cd`
> 이 문서는 위 시점에 확인된 것만 기술합니다. 계획 항목은 상태 표기로 구분합니다.

서브에이전트와 오케스트레이터가 공통으로 따르는 다섯 가지 규칙입니다. 외부 프롬프트 시리즈(@kloss_xyz)의 실행 에이전트 규칙 중 이 저장소에 없던 것만 골라 들였습니다([`D-055`](../decisions.md), 트랙 [`KLSS`](../plan/tracks/klss/README.md)). 이미 있는 규칙(계획서↔코드 충돌 멈춤, 커밋 금지, 직렬화 보호)은 원본에 두고 여기서 되풀이하지 않습니다.

| # | 규칙 | 적용 대상 |
|---|---|---|
| 1 | 문서 충돌 보고 | 전 에이전트 |
| 2 | 2회 실패 중단 | 실행하는 에이전트 (`tessera-implementer`, `tessera-verifier`, `tessera-unity-operator`) |
| 3 | 3단 보고 | `tessera-implementer`. `tessera-unity-operator`는 기존 「미해결 지점」 항목을 유지하고, 나머지 에이전트는 자기 반환 형식을 따릅니다 |
| 4 | 미확정 표기와 추정 금지 | 실행하는 에이전트와 오케스트레이터. `tessera-reader`는 「확인 못 함」, `tessera-scribe`는 `미확인`으로 같은 일을 합니다 |
| 5 | 가정 목록 | `tessera-implementer`, 오케스트레이터 |

## 1. 문서 충돌 보고

두 문서가 같은 사안을 다르게 말하면(계획서·결정 기록·`reference/`·규칙 파일끼리) 한쪽을 골라 진행하지 않습니다. 멈추고 두 위치(`파일:줄`)와 각 문구를 보고합니다. 어느 쪽이 맞는지는 사용자가 정합니다.

- 계획서↔코드 충돌은 이 규칙이 아니라 [`CLAUDE.md`](../../CLAUDE.md) 「오케스트레이션 › 규칙」(`D-041`)을 따릅니다.
- 같은 문서 안에서 오래된 서술과 새 서술이 겹쳐도 마찬가지입니다. 날짜가 더 늦은 쪽을 임의로 채택하지 않습니다.
- 충돌과 무관한 독립 항목은 계속 진행합니다.

## 2. 2회 실패 중단

같은 접근이 2회 실패하면 3번째를 시도하지 않고 멈춥니다. 보고에 시도한 방법, 각 결과, 원인(모르면 `미확정`)을 적습니다. 접근을 바꿔 다시 시도하는 것은 오케스트레이터나 사용자가 정합니다.

- 오케스트레이터의 구현↔검증 루프는 [`implement-verify.md`](../../.claude/skills/tessera-task/references/implement-verify.md)가 원본이고, `tessera-unity` 스킬 SKILL.md에도 같은 규칙이 있습니다. 이 규칙은 에이전트 한 번의 호출 안에서 도는 재시도에 적용합니다. 세는 단위가 다릅니다. 호출 안에서는 시도 2회째 실패에서 멈추고, 오케스트레이터 루프는 최초 시도 뒤 되돌림 2회까지 허용합니다.
- 「같은 접근」은 같은 호출·같은 수정입니다. 실패 원인을 새로 알아내 방법을 바꿨다면 새 접근입니다.
- Unity 응답이 오지 않는 경우(`mainThreadIdleMs` 증가)는 횟수와 무관하게 즉시 멈추고 보고합니다(`tessera-verifier` 정의의 해당 절).

## 3. 3단 보고

`tessera-implementer`는 변경 보고를 셋으로 나눕니다. 반환 형식은 이 셋에 기존 항목 `정리한 고아 심볼`과 규칙 5의 `가정`을 더한 5항목입니다(원본: `.claude/agents/tessera-implementer.md`).

- **변경한 파일** — 경로와 무엇을 왜 바꿨는지
- **건드리지 않은 파일** — 지시서 대상이거나 인접해서 바뀔 수 있었지만 일부러 두었다. 파일마다 이유 한 줄. 해당이 없으면 `없음`
- **미해결 지점** — 지시와 어긋나 못 한 것, 범위 밖이라 남긴 문제

「건드리지 않은 파일」은 범위를 지켰는지 오케스트레이터가 지시서와 대조하는 근거입니다. 이유를 적을 수 없으면 건드리지 않은 것이 아니라 확인하지 않은 것입니다. 그 경우 `미확인`으로 적습니다.

## 4. 미확정 표기와 추정 금지

모르는 값을 추정으로 채우지 않고 `미확정`이라 적어 보고합니다. 대상은 문서·보고·교훈 기록입니다. 코드의 값과 식별자에는 쓰지 않습니다.

- `미확정`은 「아직 알아내지 못함」, `미확인`은 「확인하려 했으나 못 함」, `BLOCKED`는 「외부 결정이나 선행 작업 때문에 진행할 수 없음」([`process.md`](../plan/process.md) §3)이라는 태스크 상태입니다. 서로 바꿔 쓰지 않습니다.
- 추정이 필요하면 추정이라고 밝히고 근거를 붙입니다. 사실처럼 적지 않습니다.
- 지시서가 정하지 않은 값(좌표·색·이름 등)은 임의로 정하지 말고 보고합니다.

## 5. 가정 목록

지시서나 계획서가 말하지 않았지만 결과에 영향을 주는 전제를 작업을 마칠 때 나열합니다. 작업 중에 가정이 결과를 크게 바꾼다고 판단되면(해석이 둘 이상) 진행하지 않고 멈춰 묻습니다. 영향이 작은 가정만 진행하고 보고에 남깁니다.

- 오케스트레이터는 위임 프롬프트에 정한 사항을 가정이 아닌 지시로 적습니다. 정하지 않은 사항이 가정이 됩니다.
- 심문 단계([`investigate-design.md`](../../.claude/skills/tessera-task/references/investigate-design.md) 1.5)를 거쳤다면 거기서 「근거 없이 둔 가정」으로 적은 항목을 지시서에 그대로 넘깁니다.
- 가정이 없으면 `없음`이라 적습니다.
