## 레이어: 게임 규칙

**적용 폴더**: `Assets/Scripts/Games/Yacht/`, `Assets/Scripts/Games/AugmentedYacht/Logic/` (둘 다 네임스페이스 `Tessera.Games.Yacht`)

### 해야 할 것

- **상태 변경은 명령 경로 하나로만 한다.** `YachtGameState` 는 `LocalGameAuthority` 가 단독 소유하고, 모든 변경은 `Execute(YachtGameCommand)` → `YachtGameCommandResult` 를 통과한다 — 출처: [`ADR-001`](architecture_decisions.md#adr-001-게임-상태-소유권과-싱글턴) 근거 1
- **난수는 `IRandomSource` 로 주입받는다.** 테스트가 결정론적 시드를 넣을 수 있어야 한다 — 출처: `ADR-001` 근거 1
- **매치가 끝나면 버려질 상태는 인스턴스로 둔다.** 정적으로 둘 수 있는 것은 프로세스 내내 바뀌지 않는 카탈로그(`YachtAugmentCatalog` 등)뿐이다 — 출처: `ADR-001` 결정, [`D-030`](../decisions.md)
- **권위는 결과값과 연출 시드만 내려보낸다.** 굴림 결과는 `RollPresentation` 처럼 결과값·프리셋 식별자로 표현한다 — 출처: `ADR-001` 근거 3

### 하지 말 것

- **`UnityEngine.Random`, `MonoBehaviour`, 씬 참조를 추가하지 않는다.** 난수는 주입으로 결정론을 지키고, 서버로 옮길 때 Unity 의존성을 떼어내는 작업이 생기지 않게 한다 — 출처: `ADR-001` 근거 1·3
- **게임 상태를 정적 싱글턴이나 쓰기 가능한 정적 필드에 두지 않는다.** 서버 다중 매치, 테스트 격리, 도메인 리로드가 깨진다 — 출처: `ADR-001` 근거 2
- **애니메이션 프레임이나 연출 데이터를 권위 상태에 넣지 않는다** — 출처: `ADR-001` 근거 3

## 레이어: 프레젠테이션

**적용 폴더**: `Assets/Scripts/Games/AugmentedYacht/Presentation/` (네임스페이스 `Tessera.Games.AugmentedYacht`)

### 해야 할 것

- **게임 상태는 읽기 전용 인터페이스(`IReadOnlyYachtGameState` 등)로 받는다.** 상태를 바꾸려면 `YachtGameSession` 의 메서드를 호출해 명령 경로를 탄다 — 출처: `ADR-001` 근거 1·「접근 편의성이 실제 문제라면」
- **연출은 권위가 내려준 결과값으로 재생한다.** 굴림 재생은 `RollPresentation` 의 결과값을 따른다 — 출처: `ADR-001` 근거 3
- **전역 접근이 필요하면 합성 루트에서 주입한다.** 정적 앰비언트는 읽기 전용·매치 수명 한정일 때만 쓴다 — 출처: `ADR-001` 「접근 편의성이 실제 문제라면」

### 하지 말 것

- **UI와 애니메이션이 게임 규칙 상태를 직접 바꾸지 않는다.** 아무 스크립트나 상태를 쓸 수 있으면 변경 경로가 하나라는 보장이 사라진다 — 출처: `ADR-001` 근거 2의 5
- **규칙 로직(점수 계산, 족보 판정, 증강 효과 계산)을 이 폴더에 두지 않는다.** 권위가 결정할 것과 클라이언트가 연출할 것을 나눈다. 필요하면 게임 규칙 레이어의 API를 호출한다 — 출처: `ADR-001` 근거 3
