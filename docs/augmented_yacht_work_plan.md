# 일반/증강 요트 다이스 작업 계획 및 진행 기록

## 1. 문서 목적

이 문서는 `Tessera`의 일반 요트 다이스와 증강 요트 다이스를 구현하기 위한 기준 계획서다.

작업이 중단되거나 담당자가 바뀌더라도 다음 내용을 확인해 바로 이어서 작업할 수 있어야 한다.

- 현재 구현 상태
- 지금 진행 중인 작업
- 바로 다음에 해야 할 구체적인 행동
- 단계별 범위와 완료 조건
- 이미 내린 설계 결정
- 테스트 결과와 알려진 문제
- 이전 작업 세션의 변경 내용

작업을 시작하거나 종료할 때는 반드시 이 문서의 `2. 현재 진행 포인터`와 `13. 작업 세션 로그`를 갱신한다.

### 상태 표기 규칙

| 상태 | 의미 |
|---|---|
| `TODO` | 아직 시작하지 않음 |
| `DOING` | 현재 작업 중 |
| `DONE` | 구현과 검증이 완료됨 |
| `BLOCKED` | 외부 결정이나 선행 작업 때문에 진행할 수 없음 |
| `DEFERRED` | 현재 범위에서 의도적으로 연기함 |
| `OUT` | 이번 프로젝트 범위에서 제외함 |

한 번에 하나의 작업만 `DOING`으로 둔다. 작업을 마치면 `DONE`으로 바꾸되 다음 작업은 자동으로 시작하지 않는다. 사용자가 다음 작업 ID의 시작 또는 진행을 명시적으로 언급한 경우에만 해당 작업을 `DOING`으로 지정한다.

## 3. 확정된 방향과 범위

### 3.1 구현 순서

```text
이전 증강 시스템 조사
    ↓
권위와 무관한 순수 C# 게임 코어
    ↓
일반 요트 로컬 핫시트 완성
    ↓
일반/증강 게임 모드 분리
    ↓
대표 증강 수직 구현
    ↓
증강 55개 전체 이식
    ↓
증강 시스템 그래픽 요소 완성
    ↓
증강 요트 로컬 핫시트 완성
    ↓
네트워크 지연·중복·재동기화 검증
    ↓
EOS 또는 Steam 기반 호스트 온라인 연결
```

### 3.2 현재 확정 사항

1. 일반 요트가 기본 규칙이며 증강 요트는 기본 규칙에 증강 규칙을 합성한다.
2. 외부 권위 서버보다 로컬 핫시트 구현을 먼저 완료한다.
3. 레이팅, MMR, 순위표, 승패 기반 서버 보상은 현재 범위에서 제외한다.
4. 온라인 초기 버전은 별도 권위 서버 없이 플레이어 호스트 권위를 사용할 수 있게 준비한다.
5. 게임 규칙은 `UnityEngine`, `MonoBehaviour`, 씬 오브젝트에 의존하지 않는 순수 C#으로 작성한다.
6. Unity 클라이언트는 명령을 보내고 결과를 연출하는 역할을 맡는다.
7. 주사위 값과 베이킹 프리셋 선택 결과는 하나의 명령 결과로 함께 확정한다.
8. 현재는 일반/증강 모드가 하나의 공유 씬을 사용하는 구조를 우선한다.
9. 두 모드의 아트와 배치가 크게 달라질 때만 공통 프리팹을 기반으로 얇은 별도 씬을 만든다.
10. 이전 JavaScript 코드를 줄 단위로 번역하지 않고, 동작과 테스트를 기준으로 C#에 재설계한다.

### 3.3 현재 제외하거나 연기한 기능

| 기능 | 상태 | 다시 검토하는 시점 |
|---|---|---|
| 레이팅/MMR | `OUT` | 경쟁 모드 기획 확정 시 |
| 신뢰 가능한 원격 권위 서버 | `DEFERRED` | 레이팅·재화 보상 도입 시 |
| 서버 전용 Unity 인스턴스 | `OUT` | 실시간 고빈도 게임 규칙이 생길 때 |
| 일반/증강 씬 완전 복제 | `DEFERRED` | 두 모드의 시각 구성이 실제로 달라질 때 |
| 호스트 마이그레이션 | `DEFERRED` | 온라인 기본 매치가 안정화된 뒤 |

### 4.2 현재 구조에서 주의할 점

- `AugmentedYachtController.cs`가 게임 진행, 주사위 난수, 연출, 월드 생성, 입력을 폭넓게 담당한다.
- 일반 모드 씬에서 `AugmentCardTray` 오브젝트만 삭제해도 컨트롤러가 런타임에 다시 생성한다.
- `YachtGameSession`은 점수와 턴을 관리하지만 주사위 값·종류·킵 상태를 완전히 소유하지 않는다.
- 온라인 이전 가능성을 확보하려면 주사위와 킵 상태도 직렬화 가능한 게임 상태로 이동해야 한다.
- 증강 이식은 큰 컨트롤러에 조건문을 추가하는 방식으로 진행하지 않는다.
- 기존 사용자 변경과 무관한 코드 및 아트는 수정하지 않는다.

위 구조는 책임 경계다. 실제 폴더 배치는 `D-028`에서 확정했다: 증강 관련 코드는 전부 `Assets/Scripts/Games/AugmentedYacht/` 아래에 두되, 순수 C# 로직은 `Logic/`, MonoBehaviour 프레젠테이션은 `Presentation/`으로 나눈다. 네임스페이스는 `Tessera.Games.Yacht`를 유지한다(`D-021`). asmdef 분리는 아직 하지 않는다.

### 5.2 핵심 처리 흐름

```text
UI 입력
  ↓
GameCommand
  ↓

  ↓

  ↓

  ├─ 새 상태 스냅샷

  ├─ 최종 주사위 값
  └─ 베이킹 프리셋 정보
  ↓

```

### 5.4 증강 처리 원칙

- JSON에는 ID, 이름, 설명, 대상, 표시 정보 같은 정적 데이터만 둔다.
- 실제 규칙은 컴파일되고 테스트되는 C# 처리기에 둔다.
- 범용 이벤트 버스를 과도하게 만들지 않고 고정된 처리 지점을 사용한다.
- 예상 처리 지점은 다음과 같다.

```text
OnAugmentSelected
OnTurnStarted
BeforeRoll
AfterRoll
BeforeScorePreview
BeforeScoreCommit
AfterScoreCommit
OnTurnEnded
OnGameEnded
ManualAction
```

- 증강 효과 처리 순서가 결과에 영향을 준다면 우선순위를 명시하고 테스트한다.
- 한 증강의 진행 상태는 다른 증강의 임의 딕셔너리에 섞지 않는다.

## M8. 증강 시스템 구조 리팩토링

> 이 마일스톤은 원래 `M7.5`였다. `D-029`에 따라 `M8`로 재번호했고, 하위 작업 ID도 `M7.5-Rn` → `M8-Rn`으로 바뀌었다. §13 작업 세션 로그의 과거 항목은 기록 보존을 위해 원래 ID(`M7.5-Rn`)를 그대로 둔다.

M8은 게임 규칙의 동작을 바꾸지 않고 증강 구현 구조만 재구성하는 마일스톤이다. 목적은 증강 추가 비용을 낮추는 것이며, 판단 기준은 "증강 하나를 추가할 때 새 파일 1개와 카탈로그 1줄만 필요한가"다.

현재 구조의 문제:

- `YachtAugmentRuntime.cs` 1,493줄에 45개 증강 로직이 시점별 메서드 안 `if (Owns(...))` 나열로 들어 있다. `AfterScoreCommit` 한 메서드가 250줄이다.
- `YachtAugmentHook` 플래그가 정의에만 있고 실제 디스패치에 쓰이지 않아 정의와 실행이 이원화되어 있다.
- `YachtAugmentPlayerState`가 필드 약 50개의 단일 클래스이며 `Clone()`을 손으로 관리한다. 증강 추가 시 `Clone()` 누락이 컴파일 오류 없이 상태를 잃는 버그가 된다.
- `LocalGameAuthority.UseAugmentAction`이 증강 ID 5개를 문자열 비교로 하드코딩한다.
- 점수 교체형 18개가 `YachtAugmentScoreEngine.ApplyReplacementScores`에 따로 있어 한 증강이 두 파일에 나뉜다.

목표 구조:

- 발동 시점별 인터페이스를 두고 각 증강이 필요한 것만 구현한다(`D-020`). 실제로 구현하는 시점은 현재 45개 증강에 처리기가 존재하는 것으로 한정한다(`D-024`).
- 한 증강 = 한 파일. 정의(이름·설명·대상·충돌·PhaseOneOnly), 전용 상태 클래스, 시점 로직을 같은 파일에 둔다.
- 핸들러는 `YachtGameState`를 직접 수정하지 않고 시점별 컨텍스트를 통해서만 상태를 바꾸고 이벤트를 발행한다.
- 상태 저장소는 `증강ID → IAugmentState` 맵이며 `Clone()`은 순회로 처리한다.
- 등록은 리플렉션이 아니라 명시적 카탈로그 리스트를 사용한다(IL2CPP/AOT 안전).
- `YachtAugmentRuntime`은 "보유 증강 → 시점 인터페이스 필터 → `Order` 정렬 → 호출"만 하는 디스패처로 축소한다.

## M9. 테이블 오브젝트 프리팹 이관

M9는 게임 규칙을 바꾸지 않고, 테이블 위 오브젝트를 코드 생성에서 프리팹 저작으로 전환하는 마일스톤이다. 목적은 좌표 조정에 코드 수정이 필요 없게 만드는 것이며, 판단 기준은 "씬 뷰에서 오브젝트를 옮기고 저장한 뒤 재컴파일해도 위치가 유지되는가"다.

현재 구조의 문제:

- 씬 `Augmented Dice.unity`에 GameObject가 644개 있으나 `PrefabInstance`는 0개다. 전부 코드가 생성해 씬에 구워 넣은 느슨한 오브젝트다.
- 배치 좌표가 `AugmentedYachtController.Create*()` 12개 메서드에 `new Vector3(...)` 리터럴로 직접 들어 있다(L2360~2486).
- `EnsureTableLayoutElements()`가 이미 존재하는 오브젝트의 `localPosition`/`localRotation`을 하드코딩 값으로 **다시 덮어쓴다**(L2147, L2218, L2247, L2276-2277). 이 메서드는 `Awake`와 에디터 `OnValidate`/`OnEnable`에서 호출되므로 씬 뷰 편집이 되돌아간다.
- `TabletopTrinketCluster.EnsureCluster()`가 위치를 상수로 스냅백하고(L57-62), `IsClusterMissing()`이 반지 회전이 1도만 어긋나도 클러스터 전체를 재생성한다(L70-79).
- Tabletop 컴포넌트 13개가 `[ExecuteAlways]` + `Awake`/`OnEnable`에서 지오메트리를 재생성한다.
- 메시와 머티리얼이 전부 런타임 생성이라 에셋 파일이 없다. 프리팹으로 저장할 실체가 없다.

목표 구조:

- 프롭별 메시·머티리얼·텍스처를 에디터에서 에셋으로 굽고, 프롭 단위 프리팹으로 저장한다.
- 씬은 프리팹 인스턴스만 배치한다. 배치 정보의 단일 기준은 씬 파일이며 코드가 아니다.
- 컨트롤러는 `[SerializeField]` 참조만 들고 생성·배치에 관여하지 않는다.
- 절차적 생성 코드는 삭제하지 않고 **에디터 전용 베이커**로만 남긴다. 형상을 바꾸려면 다시 굽고 프리팹에 Apply한다.

대상 프롭 14종: `HourglassTimer`, `TurnBalanceIndicator`, `RunicSlateMatrix`, `CozyCandleStand`, `RollCosmicCube`, `RollOrb`, `RerollCounterBar`, `AugmentCardTray`, `ParchmentScoreSheet`, `InkwellAndQuill`, `ParchmentPaperweight`, `TabletopTrinketCluster`(자식 3종 포함), `3D Wood Planks Table`, `3D Fabric Runner`

Assets/Editor/TabletopPrefabBaker.cs      베이커

## M9.5. 족보 표·증강 카드 UI 월드 스페이스 전환

M9로 프롭 배치가 자유로워지자 종이를 옮길 때 족보 표가 따라오지 않는 문제가 드러났다. M9.5는 그 원인을 구조적으로 제거한다.

원인은 처음 가정과 달랐다. 표는 이미 종이를 따라가도록 만들어져 있었고(`SyncOverlayTransform`이 `WorldToScreenPoint`로 재투영), 그 코드가 플레이 모드에서만 돌았을 뿐이다. 픽셀 필터 우회도 레이어 제외가 아니라 "텍스트를 3D 월드에 넣지 않는" 방식이었고, 월드 카메라 `cullingMask`는 `Everything`이었다.

화면 공간 재투영이라는 구조 자체가 취약했다. 카메라·해상도·오브젝트가 바뀔 때마다 다시 계산해야 하고 에디터에서는 아무도 계산해 주지 않으며, 회전은 표현할 수도 없었다.

## M10. 프레젠테이션 계층 리팩토링

M10은 `AugmentedYachtController`(3,096줄)를 역할별 컴포넌트로 분해하는 마일스톤이다. M8이 증강 로직에 한 일을 프레젠테이션 계층에 반복한다. M9가 씬 생성 코드 약 1,400줄을 먼저 걷어내므로 M9 이후에 착수한다.

현재 구조의 문제:

- 한 `MonoBehaviour`가 씬 생성, 주사위 비주얼, 입력 폴링, 카메라/렌더, 조명, 오디오 로딩, 턴 흐름, 증강 카드 UI 8개를 겸한다. 이 중 게임 로직 의존성이 없는 코드가 약 1,800줄이다.
- 권위 계층에 `YachtGamePhase`가 있는데도 컨트롤러가 `turnTransitionInProgress`·`hasCompletedRoll`·`isArranging`과 코루틴 핸들 2개의 null 검사로 두 번째 상태 머신을 손으로 관리한다. 동기화 보장이 없다.
- 턴 전환 지연이 `HourglassTimer`의 타이머 이벤트에 얹혀 있어, 장식 프롭을 교체하면 턴 흐름이 깨진다.
- 카드 정의 조회만을 위해 `YachtAugmentRuntime`을 두 번째로 인스턴스화한다(L99).

## M10.5. 픽셀 필터 엣지 검출 도입

M10.5 이전의 픽셀 필터는 픽셀화만 했다. 월드 렌더 타깃의 UV를 가상 격자로 내림 스냅해 최근접 샘플링하는 것이 전부였고, 뎁스·노멀 버퍼는 URP SSAO 외에 아무도 쓰지 않았다. 그래서 저해상도로 내려가면 주사위·양피지 카드·프롭의 실루엣이 배경과 뭉치고, 아트 가이드가 강조하는 챔퍼가 픽셀 단위에서 사라졌다.

M10.5는 [KodyJKing/hello-threejs](https://github.com/KodyJKing/hello-threejs)(three.js `RenderPixelatedPass`의 원본)의 엣지 검출을 URP로 옮긴다. 픽셀 격자 위에서 네 이웃의 뎁스·노멀을 비교해 뎁스 불연속은 어둡게(외곽선), 볼록한 노멀 모서리는 밝게(챔퍼 하이라이트) 만든다. 블룸과 팔레트 양자화·디더링은 범위 밖이다.

구현은 `PixelEdgeCamera`가 붙은 카메라에서만 도는 URP 렌더러 피처다. 기존 `1920×1080` 렌더 타깃과 업스케일 `RawImage` 구조는 손대지 않으므로 카메라 `pixelRect`가 그대로이고, 입력·월드 스페이스 캔버스 클릭 판정·Crisp UI 정렬이 전부 무변경으로 유지된다.

패스 시점을 `AfterRenderingSkybox`로 두는 것이 이 마일스톤의 핵심 계약이다. 코스믹 큐브처럼 스스로 빛나는 반투명 오브젝트는 그 뒤에 그려져 검은 외곽선을 받지 않는다. 아트 취향이 아니라 기술적 요구이기도 하다. URP의 뎁스 텍스처는 불투명 패스까지만 담으므로, 반투명 이후에 합성하면 큐브 뒤 배경의 뎁스로 계산한 외곽선이 큐브 픽셀 위에 덧칠된다.

## 8. 공통 완료 기준

모든 구현 작업은 다음 기준을 만족해야 `DONE`으로 변경할 수 있다.

- 요청 범위와 관련된 코드만 수정했다.
- 새 규칙에는 정상·경계·거부 사례 테스트가 있다.
- 관련 EditMode 테스트가 통과한다.
- 플레이 모드에서 주요 흐름을 직접 확인했다.
- Unity Console에 새 컴파일 오류와 예외가 없다.
- 게임 코어에 `UnityEngine.Random`, `MonoBehaviour`, 씬 참조가 추가되지 않았다.
- UI와 애니메이션이 게임 규칙 상태를 임의로 변경하지 않는다.
- 결과 재생 후 화면과 상태 스냅샷의 값이 일치한다.
- 변경 파일과 검증 결과를 작업 세션 로그에 남겼다.
- 다음 작업 포인터를 갱신했다.

테스트를 실행하지 못했다면 `DONE`으로 표시하지 않고 이유와 필요한 검증을 로그에 기록한다.

## 9. 테스트 전략

### 9.1 이전 프로젝트 기준선

이전 프로젝트 루트에서 실행:

```powershell
npm test
npm run validate:augments
```

기존 동작을 수정하는 것이 아니라 이식 기준으로 사용한다. 기존 테스트가 실패한다면 실패를 먼저 기록하고, Unity 구현이 그 실패까지 모방하도록 만들지 않는다.

### 9.2 Unity EditMode 테스트

우선 검증 대상:

- 기본 점수 계산
- 전체 턴 진행
- 난수 주입과 결정성
- 명령 유효성 검증
- 주사위 킵과 재굴림
- 증강별 점수와 상태 변화
- 증강 조합 및 처리 순서
- 명령 중복과 revision 충돌
- 상태 직렬화 왕복

테스트 파일은 규칙 영역과 가까운 이름을 사용하되 기존 프로젝트 구조를 불필요하게 대규모 변경하지 않는다.

### 9.3 플레이 모드/수동 검증

- 일반 요트 한 게임 완주
- 증강 요트 한 게임 완주
- 모든 주사위 킵 후 굴림 거부
- 마지막 굴림 후 점수 기입
- 플레이어 교대 도중 입력 차단
- 특수 주사위별 프리셋 재생
- 턴 타이머 만료
- 게임 종료 후 재시작
- 상태 스냅샷 재적용

### 9.4 회귀 원칙

증강 기능을 추가할 때마다 일반 요트 테스트를 함께 실행한다. 일반 모드의 결과가 바뀌었다면 의도된 변경인지 결정 기록을 남기기 전에는 다음 작업으로 넘어가지 않는다.

## 14. 작업 재개 절차

새 작업 세션은 다음 순서를 따른다.

1. 이 문서의 `2. 현재 진행 포인터`를 읽는다.
2. 가장 최근의 `13. 작업 세션 로그`를 읽는다.
3. `git status --short`로 기존 변경을 확인하고 사용자 변경을 보존한다.
4. 현재 작업 ID의 선행 작업과 완료 조건을 확인한다.
5. 관련 테스트를 먼저 실행해 시작 기준선을 확인한다.
6. 현재 작업이 `TODO`라면 사용자에게 시작 지시를 받기 전까지 구현하지 않는다. `DOING` 상태라면 해당 작업 범위만 구현한다.
7. 관련 테스트와 플레이 검증을 수행한다.
8. 상세 작업 상태를 `DONE` 또는 `BLOCKED`로 갱신한다.
9. 다음 작업을 자동으로 `DOING`으로 지정하지 않고 사용자 지시를 기다린다.
10. 진행 포인터와 세션 로그를 갱신한다.

### 중단 직전 최소 기록

시간이 부족해 작업을 완전히 마치지 못하더라도 다음 네 가지는 반드시 기록한다.

```text
현재 수정 중인 작업 ID
마지막으로 변경한 파일
마지막 테스트 결과
다음에 실행할 정확한 행동 한 줄
```

### 차단된 경우

- 막힌 원인을 재현 가능한 형태로 기록한다.
- 시도한 해결 방법을 기록한다.
- 사용자 결정이 필요하면 질문을 `미결정 사항`에 추가한다.
- 진행 가능한 다른 마일스톤으로 임의 이동하지 않는다.
