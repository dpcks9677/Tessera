## M7. 증강 시스템 그래픽 요소 추가

M7은 규칙 결과를 변경하지 않는 프레젠테이션 계층에서 카드, 특수 주사위, 점수표 상태, 공통 VFX를 실제 게임 품질로 완성하는 마일스톤이다. 상세 작업 상태와 사용자 협업 기록의 단일 기준은 [`docs/agent/m7_graphics_spec.md`](../m7_graphics_spec.md)에서 관리한다. 에셋 인벤토리, 카드 디자인 수정 사양, 3D 스크롤 리디자인은 그 문서 부록 A~C로 합쳤고 원본은 `docs/archive/`에 있다.

M7은 한 단계씩만 진행한다. 현재 작업을 완료해도 다음 작업은 자동으로 시작하지 않으며 사용자가 다음 작업 ID를 언급해야 진행한다. 사운드·촉각 피드백인 `M7-T10`은 사용자 결정에 따라 `DEFERRED` 상태다.

M7 완료 조건은 55개 증강의 시각적 식별, 특수 주사위 논리와 외형의 일치, 발동 주체·대상·결과의 전달, 일반 모드의 증강 전용 리소스 미생성, 그래픽과 게임 논리의 분리, 아트 가이드와 목표 해상도 통과다. 세부 조건은 전용 M7 문서를 따른다.

당시 `M7-T5`(증강 고유 아이콘 이식)까지 완료한 시점에서, 사용자 지시에 따라 M7을 중단하고 `M8`(당시 `M7.5`)을 먼저 진행한다(`D-019`). 이후 `m7_graphics_plan` 표를 재정리하면서 `M7-T5`는 "특수 주사위 외형 구현"으로 재정의됐다(과거 아이콘 이식 로그는 옛 번호 기준). 현재 표 기준 완료분은 `M7-T1`~`M7-T4`이고, 새 `M7-T5`는 8면 주사위 외형 도중 다시 중단(2026-09-05)한 뒤 픽셀 필터·셀 셰이딩 트랙(`M12`~`M16`)을 먼저 진행한다.

`D-038`에 따라 `M7-T5`~`M7-T12`를 `M17`로 옮긴다. 특수 주사위 외형, 발동 VFX, 점수표·진행형 증강 상태 표시, 수동 행동 피드백, 사운드, 그래픽 폴백, 해상도·성능 검증은 모두 "증강 요트 완주"와 분리되지 않고, 구 `M7-T7`~`M7-T9`는 `M17-T3`·`M17-T4`와 겹친다. `M7`은 카드 시각 시스템(`T1`~`T4`)으로 완결(`DONE`)한다. 흡수분은 `M17-T8`~`M17-T15`이며 `M17-T13`~`M17-T15`(사운드·폴백·검증)는 `DEFERRED`다. 이동한 작업의 시각 사양은 [`docs/agent/m7_graphics_spec.md`](../m7_graphics_spec.md)를 계속 기준으로 쓴다. `D-036`의 태그 분리 방식을 대체한다.

## M8. 증강 시스템 구조 리팩토링

> 이 마일스톤은 원래 `M7.5`였다. `D-029`에 따라 `M8`로 재번호했고, 하위 작업 ID도 `M7.5-Rn` → `M8-Rn`으로 바뀌었다. §13 작업 세션 로그의 과거 항목은 기록 보존을 위해 원래 ID(`M7.5-Rn`)를 그대로 둔다.

M8은 게임 규칙의 동작을 바꾸지 않고 증강 구현 구조만 재구성하는 마일스톤이다. 목적은 증강 추가 비용을 낮추는 것이며, 판단 기준은 "증강 하나를 추가할 때 새 파일 1개와 카탈로그 1줄만 필요한가"다.

현재 구조의 문제:

- `YachtAugmentRuntime.cs` 1,493줄에 45개 증강 로직이 시점별 메서드 안 `if (Owns(...))` 나열로 들어 있다. `AfterScoreCommit` 한 메서드가 250줄이다.
- `YachtAugmentHook` 플래그가 정의에만 있고 실제 디스패치에 쓰이지 않아 정의와 실행이 이원화되어 있다.
- `YachtAugmentPlayerState`가 필드 약 50개의 단일 클래스이며 `Clone()`을 손으로 관리한다. 증강 추가 시 `Clone()` 누락이 컴파일 오류 없이 상태를 잃는 버그가 된다.
- `LocalGameAuthority.UseAugmentAction`이 증강 ID 5개를 문자열 비교로 하드코딩한다.
- 점수 교체형 18개가 `YachtAugmentScoreEngine.ApplyReplacementScores`에 따로 있어 한 증강이 두 파일에 나뉜다.

목표 구조:

- 발동 시점별 인터페이스를 두고 각 증강이 필요한 것만 구현한다(`D-020`). 실제로 구현하는 시점은 현재 45개 증강에 처리기가 존재하는 것으로 한정한다(`D-024`).
- 한 증강 = 한 파일. 정의(이름·설명·대상·충돌·PhaseOneOnly), 전용 상태 클래스, 시점 로직을 같은 파일에 둔다.
- 핸들러는 `YachtGameState`를 직접 수정하지 않고 시점별 컨텍스트를 통해서만 상태를 바꾸고 이벤트를 발행한다.
- 상태 저장소는 `증강ID → IAugmentState` 맵이며 `Clone()`은 순회로 처리한다.
- 등록은 리플렉션이 아니라 명시적 카탈로그 리스트를 사용한다(IL2CPP/AOT 안전).
- `YachtAugmentRuntime`은 "보유 증강 → 시점 인터페이스 필터 → `Order` 정렬 → 호출"만 하는 디스패처로 축소한다.

디렉터리는 기획상 3분류를 따른다(`D-021`). 상위 경로는 `D-028`에서 `AugmentedYacht/Logic/` 아래로 옮겼다. 네임스페이스는 `Tessera.Games.Yacht`를 유지한다.

- 처리 순서에 의존하는 지점이 있으면 `Order`로 명시하고 테스트로 고정한다.

## M9. 테이블 오브젝트 프리팹 이관

M9는 게임 규칙을 바꾸지 않고, 테이블 위 오브젝트를 코드 생성에서 프리팹 저작으로 전환하는 마일스톤이다. 목적은 좌표 조정에 코드 수정이 필요 없게 만드는 것이며, 판단 기준은 "씬 뷰에서 오브젝트를 옮기고 저장한 뒤 재컴파일해도 위치가 유지되는가"다.

현재 구조의 문제:

- 씬 `Augmented Dice.unity`에 GameObject가 644개 있으나 `PrefabInstance`는 0개다. 전부 코드가 생성해 씬에 구워 넣은 느슨한 오브젝트다.
- 배치 좌표가 `AugmentedYachtController.Create*()` 12개 메서드에 `new Vector3(...)` 리터럴로 직접 들어 있다(L2360~2486).
- `EnsureTableLayoutElements()`가 이미 존재하는 오브젝트의 `localPosition`/`localRotation`을 하드코딩 값으로 **다시 덮어쓴다**(L2147, L2218, L2247, L2276-2277). 이 메서드는 `Awake`와 에디터 `OnValidate`/`OnEnable`에서 호출되므로 씬 뷰 편집이 되돌아간다.
- `TabletopTrinketCluster.EnsureCluster()`가 위치를 상수로 스냅백하고(L57-62), `IsClusterMissing()`이 반지 회전이 1도만 어긋나도 클러스터 전체를 재생성한다(L70-79).
- Tabletop 컴포넌트 13개가 `[ExecuteAlways]` + `Awake`/`OnEnable`에서 지오메트리를 재생성한다.
- 메시와 머티리얼이 전부 런타임 생성이라 에셋 파일이 없다. 프리팹으로 저장할 실체가 없다.

목표 구조:

- 프롭별 메시·머티리얼·텍스처를 에디터에서 에셋으로 굽고, 프롭 단위 프리팹으로 저장한다.
- 씬은 프리팹 인스턴스만 배치한다. 배치 정보의 단일 기준은 씬 파일이며 코드가 아니다.
- 컨트롤러는 `[SerializeField]` 참조만 들고 생성·배치에 관여하지 않는다.
- 절차적 생성 코드는 삭제하지 않고 **에디터 전용 베이커**로만 남긴다. 형상을 바꾸려면 다시 굽고 프리팹에 Apply한다.

대상 프롭 14종: `HourglassTimer`, `TurnBalanceIndicator`, `RunicSlateMatrix`, `CozyCandleStand`, `RollCosmicCube`, `RollOrb`, `RerollCounterBar`, `AugmentCardTray`, `ParchmentScoreSheet`, `InkwellAndQuill`, `ParchmentPaperweight`, `TabletopTrinketCluster`(자식 3종 포함), `3D Wood Planks Table`, `3D Fabric Runner`

Assets/Art/Generated/Tabletop/Meshes/*.asset
Assets/Art/Generated/Tabletop/Materials/*.mat
Assets/Editor/TabletopPrefabBaker.cs      베이커

굽기 도중 발견해 함께 고친 항목:

- 프리팹 파일명은 씬 오브젝트 이름을 그대로 쓴다. `SaveAsPrefabAsset`이 루트 GameObject 이름을 파일명으로 덮어쓰므로, 문자를 치환하면 프리팹 루트 이름이 씬 이름과 어긋나 이름 기반 조회가 전부 깨진다.
- 텍스처는 `EncodeToPNG`를 직접 부르지 않고 `RenderTexture` Blit 후 읽어온다. `InkwellAndQuill`이 `Apply(false, true)`로 텍스처를 읽기 불가로 만들어 두었다.
- 두 메뉴에서 모달 다이얼로그를 제거했다. REST(unity-skills)로 실행하면 모달이 Unity 메인 스레드를 막는다.
- `SyncTrayVisualMat`과 `SyncTableBackground`를 생명주기 호출에서 떼어냈다. 전자는 런타임 생성 텍스처를 머티리얼에 덮어써 구워둔 텍스처 참조를 실제로 지웠고, 후자는 테이블이나 러너가 없을 때 `BuildTableLayout`으로 전체를 재생성해 프리팹 인스턴스를 파괴할 수 있었다.

`M9-T3` 이후 컨트롤러는 3,096줄에서 2,637줄로 줄었고, 프롭 생성·배치 코드가 모두 사라졌다. 절차적 테이블·러너·트레이 생성기는 독립 컴포넌트가 없어 삭제하지 않고 `RegenerateTableSurfaces()` ContextMenu 하나로 묶어 재굽기용으로 남겼다.

굽기 이후 드러난 회귀 3건도 함께 고쳤다. 모두 "런타임 코드가 이제 구워진 에셋을 직접 덮어쓴다"는 같은 부류다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `Yacht Tray Visual` 프리팹 인스턴스가 씬에서 사라짐 | `BuildDiceGraphicsPoC`가 `[InitializeOnLoad]`로 리로드마다 실행되며, 프롭 이름이 프리팹 안으로 이동해 씬 검사가 실패하자 씬을 열어 재생성하고 저장함 | 자동 재생성 훅과 관련 메뉴 3종 제거, `RebuildTableLayoutMenu.cs` 삭제 |
| 콘솔에 "Setting the parent of a transform which resides in a Prefab Asset is disabled" 반복, 씬에 고아 오브젝트 생성 | `[ExecuteAlways]` 컴포넌트의 `OnValidate`가 프리팹 에셋 내부에서도 실행되어 지오메트리 재생성을 시도함 | `DelayEnsure*` 8곳에 `EditorUtility.IsPersistent` 가드 추가 |
| 메시·머티리얼 에셋 파일이 계속 수정됨 | `RollCosmicCube`가 테서랙트 정점을 애니메이션으로 다시 쓰는데 `sharedMesh`가 이제 에셋임. `SyncTrayVisualMat`이 런타임 텍스처를 머티리얼에 덮어씀 | 에셋이면 `DontSave` 사본을 만들어 쓰도록 수정, `SyncTrayVisualMat`·`SyncTableBackground`를 생명주기에서 분리 |

M9 완료 조건:

- 씬 뷰에서 프롭을 드래그해 저장하고 재컴파일해도 위치가 유지된다.
- 좌표 변경에 코드 수정이 필요하지 않다.
- 플레이 모드 진입 시 시각적 회귀가 없다.
- 기존 에디터 테스트가 모두 통과한다.

## M10. 족보 표·증강 카드 UI 월드 스페이스 전환

M9로 프롭 배치가 자유로워지자 종이를 옮길 때 족보 표가 따라오지 않는 문제가 드러났다. M10는 그 원인을 구조적으로 제거한다.

원인은 처음 가정과 달랐다. 표는 이미 종이를 따라가도록 만들어져 있었고(`SyncOverlayTransform`이 `WorldToScreenPoint`로 재투영), 그 코드가 플레이 모드에서만 돌았을 뿐이다. 픽셀 필터 우회도 레이어 제외가 아니라 "텍스트를 3D 월드에 넣지 않는" 방식이었고, 월드 카메라 `cullingMask`는 `Everything`이었다.

화면 공간 재투영이라는 구조 자체가 취약했다. 카메라·해상도·오브젝트가 바뀔 때마다 다시 계산해야 하고 에디터에서는 아무도 계산해 주지 않으며, 회전은 표현할 수도 없었다.

| ID | 작업 | 상태 | 완료 조건 |
|---|---|---|---|
| `M10-T1` | `CrispUI` 레이어와 카메라 컬링 분리 | `DONE` | 레이어 16이 존재하고 월드 카메라 컬링 마스크에서 제외됨 |
| `M10-T2` | Crisp UI 카메라와 화면 해상도 렌더 타깃 | `DONE` | 월드 카메라와 동일 투영의 카메라가 CrispUI만 그려 픽셀 이미지 위에 합성됨 |

- 점수 글자는 픽셀 필터를 타지 않고, 배경 테이블은 픽셀아트로 남는다.

## M11. 프레젠테이션 계층 리팩토링

M11은 `AugmentedYachtController`(3,096줄)를 역할별 컴포넌트로 분해하는 마일스톤이다. M8이 증강 로직에 한 일을 프레젠테이션 계층에 반복한다. M9가 씬 생성 코드 약 1,400줄을 먼저 걷어내므로 M9 이후에 착수한다.

현재 구조의 문제:

- 한 `MonoBehaviour`가 씬 생성, 주사위 비주얼, 입력 폴링, 카메라/렌더, 조명, 오디오 로딩, 턴 흐름, 증강 카드 UI 8개를 겸한다. 이 중 게임 로직 의존성이 없는 코드가 약 1,800줄이다.
- 권위 계층에 `YachtGamePhase`가 있는데도 컨트롤러가 `turnTransitionInProgress`·`hasCompletedRoll`·`isArranging`과 코루틴 핸들 2개의 null 검사로 두 번째 상태 머신을 손으로 관리한다. 동기화 보장이 없다.
- 턴 전환 지연이 `HourglassTimer`의 타이머 이벤트에 얹혀 있어, 장식 프롭을 교체하면 턴 흐름이 깨진다.
- 카드 정의 조회만을 위해 `YachtAugmentRuntime`을 두 번째로 인스턴스화한다(L99).

## M12. 픽셀 필터 엣지 검출 도입

M12 이전의 픽셀 필터는 픽셀화만 했다. 월드 렌더 타깃의 UV를 가상 격자로 내림 스냅해 최근접 샘플링하는 것이 전부였고, 뎁스·노멀 버퍼는 URP SSAO 외에 아무도 쓰지 않았다. 그래서 저해상도로 내려가면 주사위·양피지 카드·프롭의 실루엣이 배경과 뭉치고, 아트 가이드가 강조하는 챔퍼가 픽셀 단위에서 사라졌다.

M12는 [KodyJKing/hello-threejs](https://github.com/KodyJKing/hello-threejs)(three.js `RenderPixelatedPass`의 원본)의 엣지 검출을 URP로 옮긴다. 픽셀 격자 위에서 네 이웃의 뎁스·노멀을 비교해 뎁스 불연속은 어둡게(외곽선), 볼록한 노멀 모서리는 밝게(챔퍼 하이라이트) 만든다. 블룸과 팔레트 양자화·디더링은 범위 밖이다.

구현은 `PixelEdgeCamera`가 붙은 카메라에서만 도는 URP 렌더러 피처다. 기존 `1920×1080` 렌더 타깃과 업스케일 `RawImage` 구조는 손대지 않으므로 카메라 `pixelRect`가 그대로이고, 입력·월드 스페이스 캔버스 클릭 판정·Crisp UI 정렬이 전부 무변경으로 유지된다.

패스 시점을 `AfterRenderingSkybox`로 두는 것이 이 마일스톤의 핵심 계약이다. 코스믹 큐브처럼 스스로 빛나는 반투명 오브젝트는 그 뒤에 그려져 검은 외곽선을 받지 않는다. 아트 취향이 아니라 기술적 요구이기도 하다. URP의 뎁스 텍스처는 불투명 패스까지만 담으므로, 반투명 이후에 합성하면 큐브 뒤 배경의 뎁스로 계산한 외곽선이 큐브 픽셀 위에 덧칠된다.

| ID | 작업 | 상태 | 완료 조건 |
|---|---|---|---|
| `M12-T1` | 엣지 셰이더 | `DONE` | `DicePoC/PixelEdge`가 직교 뎁스·뷰 공간 노멀로 4이웃 엣지를 계산함 |
| `M12-T2` | 렌더러 피처와 대상 표시 | `DONE` | `PixelEdgeCamera`가 붙은 카메라에서만 패스가 등록됨 |
| `M12-T3` | 씬·리그 연결 | `DONE` | F1/F2 해상도 전환이 엣지 격자에 그대로 반영됨 |

## M13. 픽셀 필터 색 양자화

`M12`로 실루엣은 살아났지만 화면이 픽셀아트가 아니라 윤곽선을 그린 3D로 읽혔다. 측정해 보니 테이블 크롭 한 곳의 고유 색이 616색이었다. 픽셀 크기만 3×3으로 키웠을 뿐 24비트 연속 계조가 그대로 남아 있었고, 해상도를 절반으로 낮춰도 612색이 남아 그대로였다. 픽셀아트를 픽셀아트로 만드는 것은 픽셀 크기가 아니라 적은 색 수다.

양자화 코드는 원래부터 있었으나 켜면 화면이 시뻘겋게 변해 강제로 꺼 둔 상태였다. 기능 문제가 아니라 색공간 버그였다. 프로젝트가 Linear 색공간인데 선형 값을 그대로 6단계로 잘라, 어두운 웜톤 화면에서 R만 살아남고 G·B가 0으로 떨어졌다. sRGB 공간에서 양자화하면 사라진다.

M13은 이 기능을 되살리고 세 모드를 런타임에 순환한다. Off, sRGB 채널 단계, 아트 가이드 팔레트다. 팔레트는 `docs/reference/art_style_guide.md` §4 컬러 토큰 8개에서 토큰당 4단계 명암 램프를 만들어 32색을 구성한다. Bayer 4×4 디더는 가상 격자 좌표로 인덱싱해 픽셀 격자와 정합시킨다.

## M14. 트레이 확대와 보드 좌표 상수 단일화

`M13`에서 던지는 주사위를 15% 키우자 트레이가 상대적으로 좁아졌다. 착지 좌표는 `SourceToUnityScale`을 통해 `DieSize`에 비례해 함께 퍼지는데 트레이 배율은 고정 0.05였기 때문이다. 트레이 STL 메시 배율을 0.06으로 올려 여유를 회복한다.

배율을 바꾸려 하니 같은 값이 두 곳에 있었다. `DiceBoardMetrics.TrayScale`과 `AugmentedYachtController`의 `private const float TrayScale`이다. `RollSurfaceY`와 트레이 비주얼 Y 좌표도 마찬가지로 컨트롤러에 따로 있었고, 컨트롤러 쪽 Y 좌표는 `RollSurfaceY + 10.283531f * TrayScale`처럼 매직 넘버를 직접 품고 있었다. 한 곳만 고치면 바닥 높이가 어긋난다.

그래서 트레이 좌표 계열을 `DiceBoardMetrics` 한 곳으로 모은다. 매직 넘버 `10.283531`은 이미 그 파일에 `PlayFloorSourceY`로 있던 값이므로, `TrayVisualY`를 `RollSurfaceY - PlayFloorSourceY * TrayScale`로 정의하면 배율을 바꿔도 플레이 바닥이 항상 `RollSurfaceY`에 오는 것이 식으로 보장된다.

함께 플레이 영역 경계를 상수로 정의한다. 프리셋 착지 좌표를 Unity 물리로 굽는 도구가 물리벽과 착지 판정에 쓰는 값이다.

| ID | 작업 | 상태 | 완료 조건 |
|---|---|---|---|
| `M14-T1` | 트레이 배율 0.05 → 0.06 | `DONE` | 프리팹 스케일과 씬 인스턴스 Y가 새 배율과 일치함 |
| `M14-T2` | 트레이 좌표 상수 단일화 | `DONE` | 컨트롤러의 중복 상수 3개 제거, `TrayVisualY`가 배율에서 파생됨 |

| `M14-T4` | 문서화 | `DONE` | 마일스톤 요약과 실행 기록 반영 |

## M15. Unity 물리 기반 주사위 프리셋 베이커

주사위 착지 프리셋은 웹 스튜디오(`preset-studio/`, three.js + cannon-es)에서 굽고 JSON으로 `Assets/StreamingAssets/WebSource/presets`에 넣어 왔다. 프리셋 좌표는 주사위 한 변이 1.62인 소스 단위이고, Unity는 `SourceToUnityScale = DieSize / 1.62`로 스케일해 재생한다.

문제는 두 좌표계가 `DieSize = 0.78`에서만 맞물렸다는 것이다(`preset-studio/src/YachtTrayModel.js`의 `UNITY_SYNCED_TRAY_SCALE = (1.62 * 0.05) / 0.78`). `M13`에서 주사위만 0.897로 키우자 착지 좌표가 트레이 대비 15% 넓게 퍼져 주사위가 림을 뚫었다. `M14`의 트레이 확대가 여유를 되찾아 주지만, 두 좌표계가 서로 다른 경로로 스케일된다는 구조 자체는 그대로다.

그래서 베이킹을 Unity로 옮긴다. 트레이 내부 림 경계에 박스 물리벽을 세우고 PhysX로 굴린 뒤, 그 결과를 그대로 프리셋으로 만든다. 시뮬레이션 좌표계를 주사위 루트 로컬 프레임으로 두면 시뮬레이션 결과가 곧 재생 좌표가 되어, 착지가 플레이 영역 안에 들어오는 것이 정의상 보장된다. 재생 코드(`DicePresetCatalog`, `BakedDiceController`)와 JSON 포맷은 건드리지 않는다. 저장할 때 `BakedDiceController.TransformPresetDie`의 역함수로 소스 단위로 되돌려 적는다.

`preset-studio`는 손대지 않는다. 트레이 STL 원본을 만드는 코드가 거기 있다.

평가 기준은 세 가지다. 분포도는 순위 점수로 쓰고, 인식도와 판정 시간은 통과/탈락 게이트로 쓴다. "판정 시간이 구간 안에 고르게 퍼져야 한다"는 요구는 점수가 아니라 선별 방식으로 푼다. 허용 구간 1.0~2.0초를 0.05초 폭 20구간으로 나누고 구간마다 분포 점수 최고 클립을 하나씩 뽑으면, 파일당 20클립이 정확히 채워지면서 재생 길이도 함께 다양해진다.

## M16. 셀 셰이딩 전환과 픽셀 격자 정합

`M13`의 포스트 색 양자화는 색 수를 616에서 30까지 줄이고도 화면을 픽셀아트로 만들지 못했다. 가설이 절반만 맞았다. 픽셀아트를 만드는 것은 적은 색 수가 아니라 적은 평면 영역 수다. 포스트 양자화는 합성된 프레임에 걸리므로 색 경계가 밝기 그라데이션의 등치선에 생기고, 그 등치선은 휜 노멀 위에서 동심원 밴드가 되어 주사위가 구르면 표면 위를 흘러간다. 경계가 도형 경계가 아니라 렌더 경계다.

그래서 색 감축을 포스트 단계에서 재료 단계로 옮긴다. 조명 응답을 셰이더에서 2~3단 램프로 계단화하고, 시점 의존 항(스페큘러·환경 반사·프레넬)을 제거해 색 경계가 지오메트리 경계에 놓이게 한다. 주사위는 노멀을 지배 축으로 스냅해 보이는 세 면이 각각 단일 값이 되게 한다. 함께 소프트 그림자와 SSAO를 걷어내고, 1920 렌더 후 점 샘플링이라는 가짜 픽셀화를 실제 저해상도 렌더로 바꾼다.

적용 범위는 씬 전체다. 주사위만 바꾸면 3D 테이블 위에 붙인 2D 스티커로 보인다.

채택 여부가 미결정이므로 구조에 A/B와 롤백을 넣는다. `RenderStyle { Baseline, Cel }` 런타임 토글로 재료·그림자·SSAO·렌더 타깃을 한 번에 전환하고, 기본값은 `Baseline`으로 둔다. 기존 PBR 경로는 이번 마일스톤에서 삭제하지 않는다.

M16 완료 조건:

- `V` 한 번으로 Baseline과 Cel이 같은 프레임에서 왕복하고, Baseline 화면이 기준선과 일치한다.
- Cel 화면 어디에도 시점 의존 스페큘러와 소프트 반그림자가 없다.
- Cel 주사위 정지 크롭에서 바디 밝기 밴드가 3개 이하다(금속 계열 4개 이하).
- 굴림 중 픽셀 크롤 지표가 Baseline과 나란히 기록된다.
- 되돌릴 수 없는 에셋 변경의 원래 값이 문서에 기록되어 있다.
- 기존 에디터 테스트가 모두 통과한다.

### M16 매듭 (2026-09-07)

`D-037`: 셀 셰이딩 채택을 보류한다. 버리지도, 채택하지도 않는다.

- **판정 근거.** M16 완료 조건(주사위 정지 크롭 밝기 밴드 3 이하)을 충족하지 못했고, 측정에서 전제가 틀렸음이 드러났다. Baseline 주사위도 이미 면 안쪽 77 % 평면·밴드 7개라 주사위는 3D로 읽히던 원인이 아니었다. 남은 밴드는 나무결 텍스처 표면과 미변환 특수 연출 셰이더(`M16-T7`)에 있어, 그 둘을 처리해야 채택 여부를 화면으로 판단할 수 있다. 그래픽 작업은 `M17`로 모으기로 했으므로(`D-036`·`D-038`) 여기서 판단을 확정하지 않고 인프라만 남긴 채 보류한다.
- **유지하는 것.** `RenderStyle { Baseline, Cel }` 런타임 토글, `Tessera/CelSurface` 셰이더, `CelStyleSwitcher`, `PixelReadabilityMetrics`와 측정 도구를 모두 남긴다. 기본값은 `Baseline`이라 화면은 M15까지와 같다. 인프라 유지 비용은 토글 뒤 기본 Off라 낮고, 채택이 확정되면 별도 정리 마일스톤에서 Baseline 경로를 제거한다(`D-034`).
- **`M16-T7`.** `DEFERRED`. 그래픽 패스에서 Cel을 재개할 때 진행한다. 텍스처 표면 처리, 엣지 임계값 재조정, Cel 육안 비교도 함께 이월한다.
- **`M17-T19` 알파 클립 이월분(2026-09-09).** 셀 모드는 알파 클립을 나르지 않는다(`CelVariantOf`가 `_BaseColor`·`_BaseMap`·`_Metallic`만 전달하고 `CelSurface.shader`의 `frag`는 `.rgb`만 샘플하며 `clip`이 없다). `M17-T19`에서 깃펜 깃털에 알파 클립 슬릿을 도입했으므로, Cel 재개 시 `CelSurface.shader`에 `clip` 한 줄과 `CelVariantOf`의 `_Cutoff`·`_AlphaClip` 전달을 추가해야 깃펜이 Cel 모드에서 갈라짐 없이 통짜로 보이는 회귀를 막을 수 있다. `DEFERRED` 판정 자체는 바꾸지 않는다.
- **`PC_Renderer.m_RenderingMode`.** Forward(`0`) 유지. Deferred(`2`)로 복구하지 않는다. `Mobile_Renderer`가 이미 `0`이고 광원이 사실상 하나라 Deferred 이점이 없으며, Cel 재개 시 엣지 피처가 Forward를 요구한다. Baseline 외형 변화 육안 확인은 남았으나 광원 수가 적어 무시 가능 범위로 본다.
- **독립적으로 남는 성과.** 저해상도 실렌더(픽셀 크롤 4.3 % → 3.4 %)와 셀 셰이더 버그 2건 수정은 이미 트리에 있고 Cel 채택과 무관하게 유효하다.
