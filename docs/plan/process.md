# 계획 문서 운용 규칙

> **문서 종류**: 작업 규칙 (AI 대상)
> **코드 대조 기준**: 2026-10-22 · 커밋 `6527034`
> 이 문서는 `docs/plan/` 아래 계획 문서의 구조, 상태 표기, ID, 양식을 정합니다. 문서 작성 원칙 자체는 [`docs/README.md`](../README.md)를 보십시오.

## 2. 상태는 한 곳에만 적는다

ID 하나의 상태는 정확히 한 곳에만 적습니다. 같은 상태를 두 문서에 적으면 반드시 어긋납니다(2026-10 기준 `M17-T18`이 마스터 표에서 `DONE`, 하위 계획서에서 `DOING`이었던 사례).

| 대상 | 상태를 적는 곳 |
|---|---|
| 마일스톤 | `plan/roadmap.md` 표 |
| 태스크 `Mnn-Tnn` | 해당 마일스톤 `README.md`의 태스크 표 |
| 하위 작업 `Mnn-Tnn-n` | 해당 태스크 문서의 하위 작업 표 |
| 트랙 태스크 `SOLID-Tnn` 등 | 해당 트랙 `README.md`의 태스크 표 |

- 태스크 문서 머리말에는 상태 줄을 두지 않습니다.
- `STATUS.md`는 상태의 원본이 아닙니다. 진행 중인 것과 다음 행동을 가리키는 포인터입니다.
- 세션 로그에 적힌 상태는 당시 기록이며 현재 상태의 근거가 아닙니다.

## 3. 상태 어휘

| 상태 | 의미 |
|---|---|
| `TODO` | 아직 시작하지 않음 |
| `DOING` | 현재 작업 중. 여러 개를 동시에 둘 수 있습니다 |
| `DONE` | 구현과 검증이 완료됨 |
| `BLOCKED` | 외부 결정이나 선행 작업 때문에 진행할 수 없음. 사유를 적습니다 |
| `DEFERRED` | 현재 범위에서 의도적으로 연기함 |
| `DROPPED` | 범위에서 제외했거나 전제가 바뀌어 폐기함. 사유와 날짜를 적습니다 |
| `VOID` | 대상이 사라져 무효가 됨. 행을 지우지 않고 사유와 날짜를 적습니다 |

- 옛 문서의 `OUT`은 `DROPPED`로 읽습니다.
- 작업을 마치면 `DONE`으로 바꾸되 다음 작업은 자동으로 시작하지 않습니다. 사용자가 다음 작업 ID를 지목해야 `DOING`이 됩니다.
- `DOING`이 여러 개여도 대상 파일이 겹치는 태스크는 동시에 두지 않습니다. Unity Editor 조작은 한 번에 하나씩 실행합니다(`CLAUDE.md` 오케스트레이션 규칙).

## 4. ID 규칙

| 종류 | 형식 | 비고 |
|---|---|---|
| 마일스톤 | `Mnn` | 소수점 번호는 쓰지 않습니다 (`D-035`) |
| 태스크 | `Mnn-Tnn` | 마일스톤 안에서 연번 |
| 하위 작업 | `Mnn-Tnn-n` | 태스크 문서 안에서만 씁니다 |
| 트랙 태스크 | `SOLID-Tnn`, `ORCH-Tnn`, `BUILD-nn`, `LOAD-nn` 등 | 기존 ID를 유지합니다 |
| 결정 / 미결정 | `D-nnn` / `Q-nnn` | `decisions.md`에서 연번. 번호를 재사용하지 않습니다 |
| 구조 결정 | `ADR-nnn` | `docs/reference/architecture_decisions.md` |

- 번호는 재사용하지 않습니다. 비어 있는 번호는 태스크 표 아래에 `결번: M17-T20, M17-T21`처럼 밝힙니다.
- 재번호가 불가피하면 결정(`D-nnn`)으로 기록하고 `roadmap.md` 재번호 이력에 한 줄 추가합니다. 과거 로그와 코드 주석의 옛 ID는 고치지 않습니다.

## 5. 양식

### 5.1 마일스톤 `README.md`

```markdown
# M17. 증강 요트 로컬 핫시트 완성

> **문서 종류**: 마일스톤 계획 (AI 대상)
> **코드 대조 기준**: YYYY-MM-DD · 커밋 `xxxxxxx`

## 목표
한두 문장.

## 범위
- 포함: …
- 범위 밖: …

## 완료 게이트
§6 공통 완료 기준에 더해 이 마일스톤만의 조건을 적습니다.

## 태스크

### 게임 흐름·규칙

| ID | 작업 | 상태 | 수락 기준 | 문서 |
|---|---|---|---|---|
| `M17-T5` | 시간 관련 증강과 타이머 | `TODO` | 로컬 규칙 기준으로 일관되게 처리됨 | — |

### 증강 연출·VFX

| ID | 작업 | 상태 | 수락 기준 | 문서 |
|---|---|---|---|---|
| `M17-T25` | 요트 뱅크 keep zone | `TODO` | 보관 주사위가 뱅크 영역 밖으로 나가지 않음 | [T25](T25-bank-keep-zone.md) |

결번: …

## 완료 기록

### `M17-T2` 플레이어별 드래프트 UI — 2026-09-13
무엇을 바꿨고 어떻게 검증했는지. 별도 태스크 문서가 있으면 그 문서의 완료 기록을 가리키는 한 줄만 둡니다.

## 관련 결정
- `D-038` …
```

- **수락 기준 칸은 착수 전에 정하는 한 줄 기준입니다.** 구현 결과, 수정 파일, 테스트 수치는 쓰지 않습니다. 그것은 완료 기록에 갑니다.
- 완료 기록은 최신이 아래로 가는 시간순입니다.
- 태스크 표는 카테고리별 `###` 절로 나눕니다. 절 제목은 한글로 쓰고, 카테고리 목록은 마일스톤마다 그 README에서 정합니다.
- 카테고리는 ID에 넣지 않습니다. 새 태스크는 마일스톤 연번(`Mnn-Tnn`)을 받아 해당 절에 넣고, 절 안에서는 ID 순서로 둡니다.

### 5.2 태스크 문서

상세 설계, 하위 작업, 미결 질문이 있는 태스크만 별도 문서를 둡니다. 파일명은 `T<번호>-<영문 슬러그>.md`입니다.

`Q-nnn`은 `decisions.md`에 등록하고 여기서는 링크만 둡니다.

### 5.3 세션 로그 (`log.md`)

- 최신 항목이 맨 위로 오는 역순입니다. 양식은 파일 맨 위에 한 번만 둡니다.
- 헤딩: `### YYYY-MM-DD — <작업자> (<작업 ID> <요약>)`
- 본문 필드: 작업 ID / 변경 / 검증 / 다음 작업
- 시점 기록이므로 과거 항목은 고치지 않습니다.
- 어느 로그에 쓸지는 헤딩의 첫 번째 작업 ID로 정합니다. ID가 없으면 `plan/log.md`에 씁니다.

### 5.4 `STATUS.md`

30줄을 넘기지 않습니다. 세션을 새로 시작한 에이전트가 가장 먼저 읽는 문서입니다.

| 항목 | 내용 |
|---|---|
| 현재 마일스톤 | ID와 이름, 폴더 링크 |
| 진행 중 태스크 | `DOING`인 ID. 여러 개면 모두 적습니다. 없으면 "사용자 지목 대기" |
| 다음 행동 | 구체적인 한 줄 |
| 마지막 완료 | ID와 날짜 |
| 차단 요소 | 없으면 "없음" |
| 트랙 | 트랙별 남은 태스크 수 한 줄씩 |
| 마지막 갱신일 | `YYYY-MM-DD` |

## 6. 공통 완료 기준

모든 구현 작업은 다음 기준을 만족해야 `DONE`으로 변경할 수 있다.

- 요청 범위와 관련된 코드만 수정했다.
- 새 규칙에는 정상·경계·거부 사례 테스트가 있다.
- 관련 EditMode 테스트가 통과한다.
- 플레이 모드에서 주요 흐름을 직접 확인했다.
- Unity Console에 새 컴파일 오류와 예외가 없다.
- 수정한 파일이 [`control_manifest.md`](../reference/control_manifest.md)의 해당 레이어 「하지 말 것」을 어기지 않는다.
- 결과 재생 후 화면과 상태 스냅샷의 값이 일치한다.
- 변경 파일과 검증 결과를 작업 세션 로그에 남겼다.
- 다음 작업 포인터를 갱신했다.

테스트를 실행하지 못했다면 `DONE`으로 표시하지 않고 이유와 필요한 검증을 로그에 기록한다.

## 7. 테스트 정책

### 7.1 이전 프로젝트 기준선

이전 프로젝트 루트에서 실행:

```powershell
npm test
npm run validate:augments
```

기존 동작을 수정하는 것이 아니라 이식 기준으로 사용한다. 기존 테스트가 실패한다면 실패를 먼저 기록하고, Unity 구현이 그 실패까지 모방하도록 만들지 않는다.

### 7.2 Unity EditMode 테스트

우선 검증 대상:

- 기본 점수 계산
- 전체 턴 진행
- 난수 주입과 결정성
- 명령 유효성 검증
- 주사위 킵과 재굴림
- 증강별 점수와 상태 변화
- 증강 조합 및 처리 순서
- 명령 중복과 revision 충돌
- 상태 직렬화 왕복

테스트 파일은 규칙 영역과 가까운 이름을 사용하되 기존 프로젝트 구조를 불필요하게 대규모 변경하지 않는다.

### 7.3 플레이 모드/수동 검증

- 일반 요트 한 게임 완주
- 증강 요트 한 게임 완주
- 모든 주사위 킵 후 굴림 거부
- 마지막 굴림 후 점수 기입
- 플레이어 교대 도중 입력 차단
- 특수 주사위별 프리셋 재생
- 턴 타이머 만료
- 게임 종료 후 재시작
- 상태 스냅샷 재적용

### 7.4 회귀 원칙

증강 기능을 추가할 때마다 일반 요트 테스트를 함께 실행한다. 일반 모드의 결과가 바뀌었다면 의도된 변경인지 결정 기록을 남기기 전에는 다음 작업으로 넘어가지 않는다.

## 8. 마일스톤 종료와 보관

1. 카테고리 절의 모든 태스크 표, 모든 행이 `DONE`, `DEFERRED`, `DROPPED`, `VOID` 중 하나입니다.
2. §6 공통 완료 기준과 README의 완료 게이트를 확인합니다.
3. `roadmap.md`의 상태를 `DONE`으로 바꾸고 마일스톤 커밋을 진행합니다.
4. 폴더를 `git mv docs/plan/mNN docs/archive/milestones/mNN`으로 옮기고 `roadmap.md` 링크를 고칩니다.

## 9. 작업 재개 절차

새 작업 세션은 다음 순서를 따른다.

1. [`docs/STATUS.md`](../STATUS.md)를 읽는다.
2. 현재 마일스톤 `log.md`의 최상단 항목을 읽는다.
3. `git status --short`로 기존 변경을 확인하고 사용자 변경을 보존한다.
4. 이번에 다룰 작업 ID의 선행 작업과 완료 조건을 확인한다. `DOING`이 여러 개면 어느 것을 이어갈지 사용자에게 확인한다.
5. 관련 테스트를 먼저 실행해 시작 기준선을 확인한다.
6. 현재 작업이 `TODO`라면 사용자에게 시작 지시를 받기 전까지 구현하지 않는다. `DOING` 상태라면 해당 작업 범위만 구현한다.
7. 관련 테스트와 플레이 검증을 수행한다.
8. 상세 작업 상태를 `DONE` 또는 `BLOCKED`로 갱신한다.
9. 다음 작업을 자동으로 `DOING`으로 지정하지 않고 사용자 지시를 기다린다.
10. 진행 포인터와 세션 로그를 갱신한다.

### 중단 직전 최소 기록

시간이 부족해 작업을 완전히 마치지 못하더라도 다음 네 가지는 반드시 기록한다.

```text
현재 수정 중인 작업 ID
마지막으로 변경한 파일
마지막 테스트 결과
다음에 실행할 정확한 행동 한 줄
```

### 차단된 경우

- 막힌 원인을 재현 가능한 형태로 기록한다.
- 시도한 해결 방법을 기록한다.
- 사용자 결정이 필요하면 질문을 `미결정 사항`에 추가한다.
- 진행 가능한 다른 마일스톤으로 임의 이동하지 않는다.
